Implementation, step by step

13 setup steps

1. Create Server B in cPouta

A snapshot of Server A was used to create a new instance, Server B. Each server has its own floating IP and internal address:

  • Server A: public 193.166.24.18, internal 192.168.1.189
  • Server B: public 195.148.20.142, internal 192.168.1.33

2. Install MariaDB on Server B

Update the package lists, install MariaDB and the Python driver, and check the service and cloned project files:

sudo apt update
sudo apt install -y mariadb-server python3-pymysql
sudo systemctl status mariadb
ls ~/portfolio

The deployed application also installs its Python dependencies in its virtual environment.

3. Install MariaDB on Server A

Connect from the local computer using the SSH key, then update the package lists and install MariaDB and the Python driver:

ssh -i <SSH_KEY_PATH> ubuntu@193.166.24.18
sudo apt update
sudo apt install -y mariadb-server python3-pymysql

4. Create the database on Server A

Open the MariaDB console with sudo mysql, create the database and counter row, and configure the original local writer account:

CREATE DATABASE portfilio_db;
USE portfilio_db;
CREATE TABLE visitor_counter (
    id INT PRIMARY KEY,
    count INT NOT NULL DEFAULT 0
);
INSERT INTO visitor_counter (id, count) VALUES (1, 0);
CREATE USER 'app_writer'@'localhost' IDENTIFIED BY '<PASSWORD>';
GRANT SELECT, UPDATE, INSERT ON portfilio_db.* TO 'app_writer'@'localhost';
FLUSH PRIVILEGES;
EXIT;

The application uses app_writer on A. Password placeholders are not real credentials.

5. Configure Server A as the source

Edit /etc/mysql/mariadb.conf.d/50-server.cnf with sudo nano. The source settings include:

bind-address = 0.0.0.0
server-id = 1
log_bin = /var/log/mysql/mysql-bin.log
binlog_do_db = portfilio_db

Restart MariaDB with sudo systemctl restart mariadb. The database name must match exactly: the original portfolio_db filter did not log changes to portfilio_db. Network access must be restricted to the intended hosts.

6. Create the replication user on A

In the MariaDB console, create a dedicated account restricted to Server B's internal IP and inspect the source status:

CREATE USER 'replicator'@'192.168.1.33' IDENTIFIED BY '<PASSWORD>';
GRANT REPLICATION SLAVE ON *.* TO 'replicator'@'192.168.1.33';
FLUSH PRIVILEGES;
SHOW MASTER STATUS;
EXIT;

The source log file and position must match the database snapshot used to initialize B; a later status check alone is not sufficient.

7. Transfer the initial database snapshot

On A, create an InnoDB snapshot with its corresponding binary-log coordinates:

sudo mysqldump --single-transaction --master-data=2 portfilio_db > ~/portfilio_init.sql

From the local computer, transfer the dump from A to B:

scp -i <SSH_KEY_PATH> ubuntu@193.166.24.18:~/portfilio_init.sql .
scp -i <SSH_KEY_PATH> portfilio_init.sql ubuntu@195.148.20.142:~/

Use the coordinates recorded in that dump. A manual FLUSH TABLES WITH READ LOCK lock is released when its MariaDB session exits; a separate UNLOCK TABLES session cannot maintain or release it. Keep dumps private and out of the website and repository.

8. Configure Server B as the replica

Connect to B and edit its MariaDB configuration:

ssh -i <SSH_KEY_PATH> ubuntu@195.148.20.142
sudo nano /etc/mysql/mariadb.conf.d/50-server.cnf

Give B a different server ID and enable read-only mode:

server-id = 2
read_only = 1

9. Restart MariaDB on B

Apply the replica settings and check that the database service is running:

sudo systemctl restart mariadb
sudo systemctl status mariadb

10. Import the initial snapshot on B

Create the database on B and import the dump transferred from A:

sudo mysql -e "CREATE DATABASE portfilio_db;"
sudo mysql portfilio_db < ~/portfilio_init.sql

Importing a snapshot into an existing database can overwrite data; the snapshot and its recorded log coordinates must belong together.

11. Start replication and set up read access

In B's MariaDB console, use the source's internal address and the coordinates from the snapshot. The values in angle brackets are placeholders:

CHANGE MASTER TO
    MASTER_HOST='192.168.1.189',
    MASTER_USER='replicator',
    MASTER_PASSWORD='<PASSWORD>',
    MASTER_LOG_FILE='<SNAPSHOT_LOG_FILE>',
    MASTER_LOG_POS=<SNAPSHOT_LOG_POSITION>;
START SLAVE;
CREATE USER 'app_reader'@'localhost' IDENTIFIED BY '<PASSWORD>';
GRANT SELECT ON portfilio_db.* TO 'app_reader'@'localhost';
FLUSH PRIVILEGES;

The application uses app_reader on B, which has only SELECT access to the database. Never publish real passwords.

12. Check and correct the starting position

On B, SHOW SLAVE STATUS\G initially showed an I/O error because position 342 was incorrect. The recorded source position was 328. The correction used:

STOP SLAVE;
CHANGE MASTER TO
    MASTER_LOG_FILE='mysql-bin.000001',
    MASTER_LOG_POS=328;
START SLAVE;
SHOW SLAVE STATUS\G
EXIT;

These are historical values, not current setup instructions. A new replica must use the log file and position associated with its own snapshot.

13. Connect and verify the counter

The Flask application originally stored its visitor counter in an SQLite database. It was changed to use the existing MariaDB counter: Server A increments it, and Server B reads the replicated value from its own local database without incrementing it. The MariaDB counter continued from its existing value; the old SQLite database was kept.

Check that Slave_IO_Running and Slave_SQL_Running are Yes, and inspect Seconds_Behind_Master and any errors. Then load A's Week 2 page and confirm that the new count appears on B's Week 4 page without B incrementing it.

A healthy replication status alone is not enough: the database filter and the actual replicated value must also be checked.

Storage, backups & access

  • Website files: The Flask website runs from /home/ubuntu/portfolio. Its backups are stored outside the public website in /home/ubuntu/backups/portfolio on B.
  • MariaDB: Each server keeps its own local database storage. A records database changes in its binary log; B applies them to its local replica.
  • Linux access: The ubuntu account administers the servers with sudo. MariaDB runs under its dedicated mysql system account. Application database credentials are stored in a private file outside the website.
  • Database access: A's local app_writer account has SELECT, UPDATE and INSERT access to the database. B's local app_reader account has only read access. The separate replicator account is restricted to replication from B.

Website backups and continuous replication

A's ubuntu crontab runs backup-website.sh every 15 minutes (*/15 * * * *). The script creates a compressed archive of /home/ubuntu/portfolio locally before sending it to B over SSH. A dedicated key is restricted to A's internal address and B's backup receiver.

B checks the archive and stores timestamped versions in a private directory, retaining the latest 96. A logs every run and its result in ~/.local/state/portfolio-backup/backup.log. The archive excludes the virtual environment, caches and temporary status-report files. The active MariaDB database and system-level settings are not included in this website backup.

MariaDB replication continuously sends A's binary-log changes to B. The initial database dump established the starting copy; after that, B applied new changes from A. Replication is not a replacement for historical backups: a deletion, corruption, or unwanted change can also be replicated, while older backup versions let you recover an earlier state.

Verification

  • Both submitted counter pages are publicly accessible: Server A /week2/ and Server B /week4/.
  • In a public-page test, B stayed at 5 when reloaded. Loading A increased the counter to 6, which then appeared on B; reloading B again kept it at 6.
  • MariaDB reported both replication threads running and a replication delay of 0 seconds in the recorded status check.
  • Manual backups succeeded, including a test during repeated status-report updates. A page restored to a separate location matched the original by SHA-256.
  • On 22 November 2026, the 08:00 UTC scheduled backup succeeded, but the 08:15 run failed while the status report was updating. After the script was corrected, the 08:30, 08:45 and 09:00 UTC scheduled runs succeeded; the cron log and separate archives on B confirmed the runs.
  • After B was rebooted at 09:55 UTC on 22 November 2026, its website, status report and MariaDB replica were available. Loading A increased the counter from 40 to 41; B displayed 41 and reloading B did not increment it.
  • A's next scheduled backup at 10:00 UTC succeeded after B's reboot. The archive was present on B, passed integrity checks and its Week 4 page matched A's file by SHA-256.

Problem solved and lesson learned

Replication initially stopped because B had the wrong starting position in A's binary log. Checking the source status and correcting the position restored replication. I learned that the initial database copy and its matching log position must agree, and that replication keeps servers current but cannot replace versioned backups.

A later test revealed that A's binary-log filter named portfolio_db, while the actual database is portfilio_db. Correcting the filter allowed counter updates to reach B. Running replication threads alone did not prove that the correct database was being replicated.

The status report changed the website directory during a scheduled backup, causing tar to report an error. The backup now lists files without recursive directory scans, skips temporary report files and completes the local archive before sending it, so a failed archive is not transferred.
